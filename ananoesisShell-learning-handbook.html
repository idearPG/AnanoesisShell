第一章项目全景：这到底是个什么东西

1.1 一句话定义

AnanoesisShell 是一个"带 AI 副驾驶的多连接 SSH 运维终端"：浏览器/桌面壳里打开网页，就能连接 Linux 服务器敲命令、传文件， 并且可以让大模型（LLM）替你执行运维任务——但 AI 的每一个有副作用的操作（跑命令、写文件、删除）都必须经过人工审批闸门。

对标产品是腾讯云 OrcaTerm（网页版 SSH 客户端），差异点是深度集成了 AI Agent 与"人机协同"安全模型。

1.2 三种使用形态

形态说明关键设计
浏览器直连后端 Spring Boot 起在本机/服务器，前端 Vue3 页面访问 REST + WebSocket前端构建产物由后端同源托管，规避 CORS 与跨域 Cookie 问题
Electron 桌面壳v0.1.0 发布 Windows 安装包；壳拉起后端子进程后端强制绑定 127.0.0.1 回环 + 启动令牌授权（第七章详解）
数据全部本地SQLite 单文件 + 操作系统密钥库，无云端账号体系凭据密文存储，主密钥由 OS keyring 托管

1.3 仓库拓扑：Git Submodule 三仓结构

AnanoesisShell/ ← 主仓：文档、契约(contract/)、规格(openspec/)、脚本 ├── backend/ ← 子仓①：Spring Boot 3.5 后端（Java 21） ├── frontend/ ← 子仓②：Vue3 + Vite 前端 └── contract/ ← openapi.yaml + asyncapi.yaml（前后端唯一事实源）
WHY 这样设计 主仓通过 submodule 指针（一个 commit SHA）锁定前后端版本，形成"版本三元组"： 主仓某次提交 = 后端某提交 + 前端某提交。发布 v0.1.0 时三个仓库各自打 tag，指针保证可精确复现任意历史版本的完整系统。 这也是为什么每次交付要"子仓先推送、主仓再更新指针"——指针指向的 commit 必须在远端存在，否则别人 clone 后拉不到。

第二章SSH 领域入门：术语与协议原理

本章是全书的地基。读完你就能看懂 backend/src/main/java/.../ssh/ 包里 30 多个类在干什么。

2.1 SSH 是什么：不是"加密的 Telnet"

SSH（Secure Shell）协议解决三件事：加密传输（防窃听）、身份认证（防冒充）、通道复用（一条 TCP 连接跑多种会话）。 协议在 RFC 4251-4254 定义，分三层：

层职责本项目对应
传输层 Transport
RFC 4253		TCP 之上做密钥交换(KEX)、协商加密算法、服务器身份验证、完整性校验sshj 库内部完成；SshConnectionService 配置超时/keepalive
认证层 User Authentication
RFC 4252		密码、公钥、键盘交互等方式证明"我是谁"SshAuthMethod（PASSWORD/PUBLIC_KEY）、CredentialBackedSshTargetResolver 从密钥库取凭据
连接层 Connection
RFC 4254		在已认证的传输连接上开多个逻辑通道 Channel：shell、exec、sftp、端口转发…shell 通道→终端，exec 通道→Agent 命令，sftp 子系统→文件传输
WHY 通道复用很重要 一条 SSH 连接建立（密钥交换开销大，涉及非对称运算）后，开一个新 Channel 只是一次轻量消息交互。 所以本项目"一个终端 tab 连接 = 一个 SshTerminalSession（持有 SSHClient）"， 它的 shell 通道给你交互、exec 通道给 AI 跑命令、SFTP 通道传文件，共享同一份加密会话——这就是 SessionRuntime 把多角色聚合成一个对象的原因。

2.2 握手与主机密钥：为什么第一次连服务器会问"指纹对不对"

  1. 客户端连上 22 端口，双方交换支持的算法列表，用 Diffie-Hellman（或曲线25519） 协商出会话对称密钥——之后所有流量用对称加密（快）。
  2. 服务器用自己的主机私钥对握手数据签名，客户端用"已知主机列表"里的公钥验签。这一步防的是中间人攻击：如果攻击者在中间换了自己的服务器，指纹对不上。
  3. 本项目落点：sshj 的 HostKeyVerifier 接口。SshConnectionService 是全项目唯一创建 SSHClient 的地方（收口设计）， 主机密钥策略、超时、keepalive、失败分类四件事不允许散落到调用点——散落一处就有一处被绕过。
注意"首次连接信任 TOFU（Trust On First Use）+ 指纹留底"是运维客户端的标配话术。测试代码里 verify() 返回 true 的宽验签只允许出现在嵌入式测试服务器场景，生产路径必须校验指纹。

2.3 PTY——本章最重要的术语

PTY（Pseudo-TERMinal，伪终端）是操作系统提供的一对虚拟字符设备，模拟"插了一台终端机"：

PTY 主端 (master, /dev/ptmx) ←——— 内核里的"管道+线路规程" ———→ PTY 从端 (slave, /dev/pts/0,1,2...) 你的程序（SSH 服务端）在这里读写 程序（bash/vim/top）以为自己在和真实终端对话
  • 程序输出 ls 结果时从端是"显示器"；你敲键时从端是"键盘"。
  • 从端有行规程（line discipline）：处理 ^C（SIGINT）、^?（SIGQUIT）、退格、以及 ECHO 回显——你在终端敲的字符会被内核原样打回来，这就是"你看到的字是回显，不是程序打印的"。
  • 为什么 SSH 必须要 PTY：没有 PTY，bash 认为自己处在脚本环境——不打印提示符、不加载交互式配置、vim/top 直接罢工（它们需要 ioctl 设置终端尺寸、raw mode）。 SSH 客户端请求"pty-req"通道扩展，远端 sshd 就分配一个 PTY 并把 bash 的 stdin/stdout/stderr 全接到从端。
  • 尺寸同步：窗口缩放时客户端发 window-change 消息，sshd 用 TIOCSWINSZ ioctl 改从端尺寸，bash 收到 SIGWINCH 重排版——xterm.js 的 fit 插件算出行列数，通过我们的 WebSocket TerminalInput.resize 传到后端。
WHY 本项目共享一个持久 PTY Shell 模式（人敲）和 Agent 模式（AI 注入命令）共用同一条 shell 通道的 PTY，而不是各开一条。 理由：AI 的工作目录、环境变量、后台进程必须和你手敲的完全一致（你在 shell 里 cd /opt/app 后问 AI"看下日志"，AI 必须知道自己在 /opt/app）。 代价是输入权争用——这直接催生了第五章的 PtyCommandScheduler 状态机。这是一个"用复杂度换正确体验"的典型取舍。

2.4 终端不只是字符流：ANSI/VT 转义序列

终端输出流里混着两类字节：可见文本和控制指令（以 ESC=0x1B 开头的转义序列）：

序列含义项目中出现的位置
ESC[31m / ESC[0mCSI 序列：设置红色/复位——颜色和光标移动都靠 CSIxterm.js 渲染 ls --color；CSP 曾误拦 xterm 动态样式表导致终端掉色（known-issues）
ESC]0;文本 BELOSC 序列：设置窗口标题。OSC 是"带字符串参数的系统指令"Shell 集成的命脉：项目用自定义 OSC 帧在字节流里打"命令边界"暗号（5.4 节）
惰性提示符bash 的 PS1 只在有键盘输入被 readline 处理时才刷新导致"AI 执行完提示符不出来"类 BUG——必须服务端主动补画（架构记忆：回合收尾链路）

2.5 exec 通道 vs shell 通道 vs SFTP 子系统

方式特点本项目用途
exec（ssh exec / Channel）一条命令、拿完 stdout/exit code 就走；没有 PTY（默认），无状态SshExecService：只读工具兜底、失败分类采集；Agent 命令在 shell 集成未装成功时"回落 exec"
shell（PTY + 交互 bash）有状态（cwd/env 延续）、输出是字节大海（混杂回显/提示符/ANSI）人机共用主通道；SshTerminalSession
sftp（子系统子系统）SSH 通道上跑 SFTP 协议——结构化的 打开/读目录/写文件 RPCSftpService 列目录/浏览 + TransferService 传输

SFTP ≠ FTP：FTP 是明文、双 TCP 连接（21 控制 + 被动模式数据）的远古协议；SFTP 是 SSH 的子系统 （subsystem sftp 请求复用加密通道），天然加密、天然认证、单连接。FileTransfer 表管的是 SFTP 传输任务的生命周期。

第四章架构与设计思想：这套系统是怎么想问题的

4.1 分层：controller → service → ssh/ai 领域包，entity/mapper 数据壳

controller/ REST 适配层（只做状态码翻译与参数搬运，薄） service/ 业务编排（Host/Session/Conversation/Transfer 生命周期） ssh/ SSH 领域：连接、PTY、shell 集成、命令调度、SFTP ← 本书重点 ai/ Agent 领域：模型接入、上下文构建、工具、think 解析 approval/ 审批闸门（横切：AI 副作用操作的人审关卡） security/ 凭据加密、令牌、票据、审计脱敏（横切安全层） desktop/ 桌面壳协同：回环守卫、启动令牌、优雅关闭 ws/ WebSocket 协议层：三条通道的 handler + 帧模型 entity/ mapper/ config/ support/

判断一个类放哪层的试金石："换一个 Web 框架它还要不要？"要 → 领域包；不要 → controller/ws。

4.2 核心设计原则（从代码注释里"考古"出来的 WHY）

原则一：唯一收口（Single Funnel）

全项目只有 SshConnectionService 能创建 SSHClient。因为超时、主机密钥策略、keepalive、失败分类这四件事， 任何一件散落到调用点，就会有一个调用点漏配。同类应用：只有 TransferContentController 碰下载流；只有 SessionControlService/ticket 服务持有敏感令牌。

原则二：状态机显式化，拒绝"如果……就……"式的散落判断

两处最重的状态机：PtyCommandScheduler（谁拥有 PTY 输入权）与 ApprovalGate（审批票据生命周期）。 显式状态 + 合法迁移写在一个类里，非法迁移直接不可表示。副作用是并发 bug 无处藏身。

原则三：降级路径是设计出来的，不是碰运气

  • shell 集成只认 bash——非 bash（csh/fish/受限环境）时：不写钩子、不装调度器、不动输出链，人工终端与 SFTP 完全不受影响，Agent 命令回落 exec 通道。
  • OS 密钥库不可用：应用照常启动（只告警），给用户留"改用主密码"的自救通道——把启动变成硬门禁等于锁死唯一生路。
  • 下载票据机制失效场景：宁可 409/404 明确拒绝，不放行"看起来大概也许没问题"的传输。

原则四：协议上"能测"优先于"能跑"

WS 帧测试坚持手写裸 JSON 字符串而不是构造 Java 对象再序列化：自造帧会抵消注解写错键名的风险—— 线上真实的契约是 snake_case 字节，测试必须锚定字节而不是锚定对象。这一条是契约驱动开发的最后一公里。

原则五：内存有界（Bounded Memory）

场景界限实现
上传/下载文件（最大 10 GiB）恒定 64 KiB 缓冲TransferContentController 用 servlet 原始流 + StreamingResponseBody，绝不 Resource 全量加载
终端断线重连补屏tail 环形缓冲TerminalWebSocketHandler 只留尾部若干 KB + gap 检测（补不齐就明确告知"有缺失"）
命令输出采集64 KiB 采集上限超限继续排空 PTY、只丢弃超额内容——排空是为了不堵死对方
审批帧出站积压512 KiB 即断开ConcurrentWebSocketSessionDecorator；超限=前端已死，留着只会白占内存

4.3 三条 WebSocket 通道为什么分开

通道方向帧为什么单独一条
/ws/terminal双向，高频字节输出块/输入键/resize性能敏感（每键每字节流经），协议与业务无关，不能和 JSON 控制帧抢一条连接的语义
/ws/ai服务器推为主token 流/think/tool 事件/回合边界流式 LLM 输出节奏特殊（增量+可中断），停止按钮要能掐断
/ws/approval双向，低频小帧approval_request / approval_response审批是全局广播+带超时的人机交互，缓冲策略（512KiB）与终端（更大）不同；分开才能独立做背压策略

4.4 前端同源托管 vs 自定义协议加载（一次被推翻的设计）

决策案例Electron 传统做法是 file:// 或自定义协议加载页面。本项目选择后端 HTTP 同源托管： ① CSP、Cookie（HttpOnly）、相对路径 API 全部天然工作，不必为自定义协议重写安全边界； ② 打包产物校验时发现两条加载路径的差异会制造"开发正常、打包掉色"类环境性 bug（CSP style-src 拦截 xterm 动态样式表事件）； ③ 桌面壳只剩"起进程 + 开窗 + 传令牌"三件事，复杂度全留在可测试的 Java 侧。被否决方案的成本在 known-issues 里留下了真实学费。

第五章终端链路深潜：PTY、命令帧与调度状态机

5.1 一条 SSH 连接的完整生命周期（SshConnectionService + SshTerminalService）

  1. 解析目标：CredentialBackedSshTargetResolver 按 hostId 从凭据库解密出 SshTarget（明文密码只活在内存 SecretText 里，用后即焚——它实现了可擦除的 char[] 语义，而不是 String）。
  2. 握手与认证：sshj SSHClient.connect() → 验主机密钥 → password 或 publickey 认证（支持 OpenSSH v9 / PKCS8 / PuTTY 格式私钥，加密私钥用 PasswordFinder 现取现用）。
  3. 申请 PTY + shell：client.sh() internally 发 pty-req + shell 两个通道消息；SshTerminalSession 包装 Shell，起两条读泵线程分别盯 stdout/stderr。
  4. 登记：SessionRuntime（聚合：SSH 会话 + 录制器 SessionRecorder + 调度器）注册进 TerminalSessionRegistry；DatabaseSessionRecorder 把会话元数据落到 SQLite 的 sessions 表。
  5. 保活与回收：SSH keepalive 探测半开连接；TerminalIdleReaper 定时巡检——浏览器崩了没人发关闭帧，空闲超时后服务端主动断开，不然 PTY/线程/远端 sshd 进程会泄漏。
  6. 失败分类：SshFailureKind + SshCloseReason 把 ConnectException/NoRoute/Auth 失败/算法协商失败等归类，前端才能给出人话错误而不是 stack trace。

5.2 网页终端怎么显示：WebSocket 桥接（TerminalWebSocketHandler）

后端本质是一个双向泵：PTY 字节 → UTF-8 解码 → WS TextMessage → xterm.js term.write()；键盘反之。 但纯转发不够，本项目加了三层工业级处理：

  • tail 环形缓冲 + gap 检测：WS 断了重连，新连接上来先回放缓冲里的最近输出；如果断线期间产生的输出已溢出缓冲（有缺口 gap），帧里明确携带"有缺失"标志——宁可告诉你缺，绝不假装完整。
  • ConcurrentWebSocketSessionDecorator：一条 WS 会话同一时刻只允许一个线程发送（协议规定），装饰器做发送锁+字节上限+时间上限，防止慢客户端把服务端内存顶爆。
  • 帧协议精简：终端通道不塞 JSON 业务帧（那是 ai/approval 通道的事），保证高频字节流的低开销。

5.3 核心难题：怎么从"字节大海"里知道一条命令跑完了？

PTY 输出是无结构的字符海：回显、提示符、ANSI 序列、程序输出混在一起。AI 执行 mvn package 后凭什么说"完成了，退出码是 1"？ 答案：Shell Integration——用 OSC 转义序列在字节流里打暗号。

向 bash 注入钩子（PROMPT_COMMAND / 调试陷阱），让 bash 在命令边界打印不可见控制帧： $ mvn package ESC]1337;CMD_START{id=42,cmd=...}BEL ← 命令开始（回车被 readline 消费时） [大量正常输出…] ESC]1337;CMD_END{id=42,code=1}BEL ← 命令结束+退出码 ESC]1337;PROMPT{seq=7}BEL ← 提示符真正画出来了=PTY 空闲可注入 服务端 ShellFrameDecoder 逐字节剥离这些 OSC 帧，转成干净文本+事件； 没装钩子的普通终端里它们是非法 OSC，被 xterm.js 直接忽略——协议对人不透明。
踩坑实录（known-issues #14）安装钩子代码是"打"进交互式 bash 的，bash 的 readline 会自己回显你敲给它的字符——这不受 tty ECHO 标志控制（stty -echo 压不住）！ 回显出来的还是安装脚本的字面源码，解码器也剥不掉。唯一可靠治理点：服务端闸门——写安装代码之前先把输出链切到闸门监听器， 吞掉"首个真实控制帧到达前"的一切转发，钩子生效后自动放行；超时兜底防止把用户终端哑掉。教训：tty 之下皆字节流，你以为关掉的开关可能根本不管这段路。

5.4 PtyCommandScheduler：谁拥有共享 PTY 的输入权

状态机（每会话一个实例）：

manual_idle ──AI领任务──▶ agent_owned ──CMD_END+PROMPT──▶ manual_idle ▲ ▲ │ │ └──无输出超时/中断无证据──▶ unknown（保守：什么都不注入） │ manual_busy（用户半行输入/粘贴/全屏程序/嵌套shell中——禁止注入） └ 自愈：用户停手超过 busy 时限且无 CMD_START 证据 → 清行回落 idle
  • 串行执行：并发写入共享 stdin 会让输出交错到无法归属，所以一条命令必须拿到"CMD_END+PROMPT 双证据"才允许下一条。
  • 双层超时（BUG-A 教训）：旧版"30 分钟绝对超时"把持续输出的 yum install 误杀了。新语义：60 秒无任何输出/帧活动才算卡死，命令只要还在说话就视为活着；30 分钟绝对上限只兜底。
  • manual_busy 死锁案例（最有价值的 bug）：用户按"停止回合"后键盘活动把状态标成 busy → busy 状态下 AI 提交被拒、不发命令 → 不发命令就没有 PROMPT 帧 → 而 busy 的旧唯一恢复证据恰恰是 PROMPT 帧。"拒绝 → 无帧 → 永久 busy"的自锁闭环，恢复证据依赖被自己拒绝的事件。修复：busy 增加"无 CMD_START 证据即可自愈"的独立出口。教训：设计状态机时，每个阻塞态必须问一遍——它的恢复证据会不会被这个状态本身掐断。

5.5 重连语义：reset agent memory on reconnect

WS 断开重连后，终端画面可以靠 tail 缓冲补齐，但 LLM 的对话上下文不能靠猜：断线期间用户手动敲了什么，模型一无所知。 所以规格明确：重连时重置该会话的 Agent 记忆，防止模型基于过时状态行动。"补屏"与"补上下文"是两个性质完全不同的问题。

6.3 模型接入与上下文工程

  • OpenAI 兼容统一收口（OpenAiCompatibleChatModelProvider）：无论背后是 OpenAI/DeepSeek/Ollama，只走一套 base_url + /chat/completions + api_key。项目规矩：模型配置只允许这三样，杜绝各家 SDK 分裂。
  • InlineThinkTagParser：不少兼容网关不返回独立 reasoning 字段，而是把思考混在正文 <think> 标签流里。逐 token 增量解析这个流（标签可能被切片跨帧），把"思考"与"答案"分流到不同前端渲染。
  • AgentContextBuilder + ContextTokenEstimator + ContextLimitClassifier：终端输出是 token 黑洞（一条命令几十 KB 输出）。构建上下文时估算 token、超限分类处理（截断策略要显式，不能让 SDK 默默截走关键信息）。
  • 回合收尾不变量：AI 回答结束 → 终端必须自动换行、画出待输入提示符、光标就位——不等用户敲键盘。"状态变更结束时自绘到位"是产品验收红线（与"Shell/Agent 切换不得有连接中提示"同源）。

第七章安全设计：本地授权、凭据加密，以及 JWT 原理对照

7.1 先建立框架：这个项目的安全模型不是"网站登录"

传统 Web 安全三件套是 账号体系 + Session/JWT + RBAC。本项目的场景完全不同：单用户、本机运行、进程间通信。 它防的不是"别人登录我的号"，而是：

  1. 局域网/本机其他进程冒充浏览器调用这个"能执行任意 SSH 命令"的后端 → 桌面授权模型解决；
  2. 磁盘上的敏感数据泄密（SQLite 被拷走、内存 dump、日志泄露）→ 密钥库信封解决；
  3. 协议层攻击（路径穿越、缓存投毒、时序侧信道）→ 逐项加固解决。

7.2 桌面授权：回环绑定 + 启动令牌 + HttpOnly Cookie

Electron 壳启动时：生成随机启动令牌 → 环境变量注入后端子进程 浏览器页面加载 → 携令牌 POST → DesktopGuardFilter 校验 → 下发 HttpOnly 会话 Cookie 此后所有 REST/WS 必须带 Cookie，否则 401 同时 server.address=127.0.0.1 显式绑定（Spring Boot 默认 0.0.0.0 —— 那会把任意 SSH 执行端口暴露到局域网！）
WHY 这不是多此一举"客户端无需登录"≠"无授权"。Cookie 存在证明调用方是从壳里加载的页面， 而不是本机恶意进程直接 curl 127.0.0.1:8080。配合回环绑定，攻击面从"整个网络"缩到"本机同用户"——而本机同用户能干的坏事（直接读你的私钥文件）本来就不需要攻破这个端口。

7.3 顺带把 JWT 原理学了——然后说明为什么这里不用它

JWT 是什么

JSON Web Token = 三段 Base64URL 用点连接：header.payload.signature

eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJ1c2VyLTEyMyIsImV4cCI6MTcz... . SflKRx... {alg:HS256,typ:JWT} {claims: sub/exp/iat/jti/自定义} 签名
  • 签名算法：HS256（对称，服务端一把密钥 HMAC 签名，适合单体自签自验）；RS256/ES256（非对称，认证中心私钥签、资源服务公用公钥验，适合微服务/第三方接入）。
  • 校验流程：服务端不查库，重算一遍 HMAC 对比签名 → 签名真 + exp 未过期 → 直接信任 payload 里的身份。这就是"无状态"的含义与优势：水平扩展不需要共享 session store。
  • payload 只是编码不是加密：Base64URL 人人可解，所以 JWT 里绝不放敏感数据，完整性全靠签名。
  • 经典难点（背下来面试必问）：无法主动失效——token 在 exp 前永远有效。注销/封号要靠黑名单（又回到查库）、短 exp+refresh 轮换、或 jti 撤销表。

JWT vs Session vs 本项目的启动令牌

JWT传统 Session本项目（启动令牌→HttpOnly Cookie）
状态在哪无状态，全在 token服务端内存/Redis服务端 DesktopSessionStore 内存
主动撤销难（需黑名单）删一条即失效重启后端进程即全部作废（本地场景天然短生命周期）
适用场景多服务、跨域、水平扩展单体、集中会话单用户、本机、零账号体系
本项目取舍不用 JWT 的理由：①没有"多实例横向扩容"需求，无状态优势用不上；②端口一旦泄露危害极大，需要即时可撤销的授权，无状态 token 反而做不到；③引入 JWT 意味着签名密钥管理、过期刷新链路——为一个永不联网认证的场景增加真实攻击面。安全设计的铁律：机制的复杂度必须有对应的威胁模型来买单。

7.4 凭据加密：信封格式 + OS 密钥库主密钥

用户存进 SQLite 的 SSH 密码/私钥/模型 API Key，都是这样一行密文：

"v1." + Base64URL( { "v":1, "kp": "os-keyring" | "master-password", ← 用哪把主密钥解 "iv": <12B b64>, ← AES-GCM 随机向量 "ct": <密文+GCM认证标签>, "salt": <16B>?, "it": 迭代次数? } ) ← 仅主密码路径需要
  • 信封自描述：密钥来源、算法参数、KDF 元数据全在密文自己身上，"密文与解密所需信息永不分离"。将来调高 PBKDF2 迭代次数，历史密文照样解得开（salt/it 跟着密文走）。
  • AES-256-GCM：认证加密（AEAD）——不光保密，GCM 标签还保证没被篡改；12 字节 IV 一次一用。
  • 两级主密钥：优先 OS keyring（Windows 凭据管理器/macOS Keychain，密钥不落盘）；不可用则主密码经 PBKDF2 高次迭代派生。密钥库缺失时只告警不拒启动——否则用户没了改配置的自救通道。
  • SecretText：明文凭据用可擦除容器承载，用后清零，不留 String 常量池尸体。

第八章SFTP 文件传输：大文件不过内存的完整案例

8.1 为什么上传下载不走 JSON/REST 常规路

常规 Spring MVC 用 @RequestBody Resource 接文件 = 先把整个文件（最大 10 GiB）缓冲到磁盘临时文件再包装，内存/磁盘双爆炸； Base64 入 JSON 更是膨胀 33%。所以 openapi.yaml 里 TransferContent 标了 x-skip-codegen: true——契约先行也有边界，生成器做不了的流式端点手写，但契约文档照写不误。

8.2 下载全链路（面试可整段背诵）

① POST /transfers/{id}/ticket 领票（256-bit 随机，服务端只存散列，领新废旧，≤30 分钟） ② GET /transfers/{id}/content?ticket=xxx → startDownload：原子消费票据 + 状态 READY→TRANSFERRING（并发抢同一票只有一个成功） → 返回 StreamingResponseBody：64 KiB 循环搬运 SFTP 流 → HTTP 响应流，恒定内存 → finally completeDownload 更新状态（失败只告警不击穿响应流） 安全头三件套：no-store / Referrer-Policy: no-referrer / Content-Disposition（RFC 6266： ASCII 回退名 + UTF-8 filename* 双写，非 ASCII 字符替换为下划线，控制字符不留）
  • 为什么要票据而不能"直接 GET 就下"：GET 无请求体、浏览器地址栏/Referer/历史都会泄露 URL，一次性短效票据把"下载授权"从 URL 长期有效降级为短窗口单次有效；即使泄露，消费即废。
  • 为什么状态机卡这么严（queued→ready→transferring→completed/failed/expired）：传输任务是跨进程生命周期的资源，任何一步都可断点可观测；配额（并发槽位）检查只在创建时做，防止把远端 sshd 连接打爆。
  • 每会话 SFTP 句柄上限 2（SftpService.MAX_HANDLES_PER_SESSION）：句柄是远端资源，泄漏一个就是在客户机器上留一个坑；分页游标也有 TTL（CursorExpiredException）。

9.3 JaCoCo 分支覆盖率门禁：数字背后的方法论

  • 门槛写在 pom.xml 的 jacoco:check 规则（counter=BRANCH, COVEREDRATIO ≥ 0.70），mvn verify 不达标直接 BUILD FAILURE——门禁的意义是不可绕过，可绕过的门禁等于没有。
  • 为什么用分支覆盖而不是行覆盖：行覆盖 90% 的系统可能每个 if 的 else 从没走过；AI 生成代码最典型的盲区就是异常分支和边界条件没被验证，分支覆盖率恰好打的在这个穴门上。
  • 渐进式策略：0.65 基线测量 → 0.70 门禁 → 补测试（复活被禁用的 SftpServiceTest 一次捡回 50 个分支，新建两个测试类再补 36 个）——先基线、再卡门、再补，顺序不能反。
  • Git hooks 双闸门：pre-commit 按改动子仓跑对应门禁，pre-push 跑测试+覆盖率；AI 参与的代码库里，机械闸门比人工 review 更早拦截回退。

9.4 并发与资源管理专题（散布在各类的隐性知识）

  • 读泵线程：SSH 输出必须专人专线程阻塞式读（不读会背压堵死远端），用 CopyOnWriteArrayList 承接并发写。
  • Future.get 双层超时陷阱：等待方超时必须晚于执行方调度器超时，否则等待方先抽风、执行方还在干活——"谁超时谁负责"要有全局序。
  • Windows 子进程不跑 shutdown hook：强杀 Electron 子进程时 JVM 优雅关闭不执行，必须显式 IPC（DesktopShutdownController 收尾 REST 调用）代替隐式钩子。
  • 出站缓冲超限即断：WebSocket 发送锁竞争下慢消费者的帧会在装饰器缓冲里堆积，超过 512 KiB 抛 SessionLimitExceededException——handler 主动关连接并移出活跃表而不是重试：前端已死，留着只会每次广播都白跑一趟。

10.2 面试官会顺着简历问什么（附答案锚点）

"PTY 到底是什么？为什么 SSH 需要它？"
主/从设备对，从端给程序一个"真终端"幻觉（行规程/ECHO/ioctl 尺寸）；无 PTY 则 bash 非交互、vim 不可用；SSH 用 pty-req 请求远端 sshd 分配。（详 2.3）
"你怎么知道一条命令执行完了？退出码哪来的？"
bash 钩子（PROMPT_COMMAND）发 OSC 控制帧，服务端解码器剥离并解析 CMD_END 携带的退出码；非 bash 降级 exec 通道拿协议层 exit-status。（详 5.3）
"人和 AI 共用一个终端，怎么防打架？"
输入权状态机：只认"空提示符"证据才注入，人工半行/粘贴/全屏程序一律 busy；串行 + 双证据推进；busy 有独立自愈出口。（详 5.4）
"为什么不用 JWT？那 JWT 原理说说？"
三段式签名令牌，无状态验签、难主动撤销；本项目单用户本机场景需要即时撤销授权且无扩容需求，启动令牌+HttpOnly Cookie 攻击面更小。能讲清"机制复杂度必须由威胁模型买单"即是满分答案。（详 7.3）
"密码存在数据库里怎么算安全？"
不存密码存信封密文；加密两层：数据密钥 AES-GCM 一次一密，主密钥交 OS 密钥库或 PBKDF2 派生；参数自描述保证算法可演进。加分点：密钥库不可用时"告警不拒启动"的自救设计。（详 7.4）
"10GiB 文件下载怎么不把服务端的内存干掉？"
不反序列化、不 Resource 包装，SFTP 流→64KiB 循环→StreamingResponseBody；票据原子消费防重放；completeDownload 失败不击穿已开流的 finally 收尾。（详 8.2）
"AI 写的代码你怎么保证质量？"
分支覆盖率而非行覆盖率（AI 盲区在异常分支）；门禁不可绕过（mvn verify + pre-push）；协议测试验证线上字节而非 Java 对象；真协议栈集成测试而非 mock。（详第九章）
