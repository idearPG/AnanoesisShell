## 1. 终端文本复制粘贴功能

### 1.1 问题

当前 xterm 终端不支持鼠标选中文本后右键复制粘贴。用户无法通过常规操作复制终端输出内容（命令、路径、日志片段等）。

### 1.2 方案

使用 xterm.js 官方 `@xterm/addon-clipboard` 实现剪贴板集成，配合 `rightClickSelects` 选项启用右键选择，并实现自定义右键菜单（含复制/粘贴按钮）。关键约束：**Ctrl+C 快捷键不得与现有中断功能冲突**。

### 1.3 实现细节

**新增依赖**：
- `@xterm/addon-clipboard` — xterm.js 5.x 官方剪贴板 addon

**Terminal 初始化配置**（`frontend/src/components/terminal/TerminalTimeline.vue`）：
- 添加 `rightClickSelects: true` — 右键单击选择文本（终端客户端惯例）
- 加载 `ClipboardAddon` — 启用系统剪贴板互通（但不自动绑定 Ctrl+C/Ctrl+V，见下方冲突处理）

**Ctrl+C 冲突解决（关键）**：
- 当前 Ctrl+C 在 Shell 模式发送 `\x03`（中断信号），在 Agent 模式升级为打断回合
- `ClipboardAddon` 默认会注册 Ctrl+C 为复制快捷键，与上述行为冲突
- **解决方案**：不依赖 addon 的默认键绑定，而是自定义 Ctrl+C 处理逻辑：
  - 有文本选中时 → Ctrl+C 复制选中内容到剪贴板（不发送中断）
  - 无文本选中时 → Ctrl+C 保持原有行为（Shell 发 `\x03` / Agent 打断回合）
- 实现方式：在 `terminal.attachCustomKeyEventHandler` 中拦截 Ctrl+C，根据 `terminal.getSelection()` 判断分流
- Ctrl+V 粘贴不冲突，可直接由 `ClipboardAddon` 处理（粘贴不覆盖任何现有快捷键）

**自定义右键菜单（本期纳入）**：
- 禁用 xterm 容器上的浏览器默认右键菜单（`contextmenu` 事件 `preventDefault`）
- 渲染自定义浮动菜单，包含：
  - 「复制」按钮：将 `terminal.getSelection()` 写入剪贴板；无选中时禁用
  - 「粘贴」按钮：从剪贴板读取内容，通过 `sendInput` 发送到 PTY
- 菜单定位跟随鼠标点击坐标，点击菜单外区域自动关闭
- 样式延续现有深色主题（`#161b22` 背景、`#c9d1d9` 文本、`#30363d` 边框）

**Electron 桌面端**：
- `rightClickSelects` 在 Electron 环境同样生效
- 自定义右键菜单在 Electron 中需验证不被原生菜单拦截
- CSP 策略不拦截右键事件与自定义菜单 DOM

### 1.4 影响范围

- 前端：`TerminalTimeline.vue`（初始化配置 + addon 加载 + 右键菜单组件 + 键绑定拦截）、`package.json`（新依赖）
- 测试：`TerminalTimeline.spec.ts` 补充剪贴板分流、右键菜单、Ctrl+C 冲突处理用例
- 不涉及后端/契约变更

### 1.5 验证场景

1. 鼠标拖选终端文本 → 文本被高亮选中
2. 右键单击选中文本 → 弹出自定义菜单，「复制」可用 → 点击后内容进入剪贴板
3. 右键单击无选中区域 → 弹出菜单，「复制」禁用、「粘贴」可用 → 点击粘贴后内容发送到 PTY
4. **有选中文本时** Ctrl+C → 复制到剪贴板，**不触发中断**
5. **无选中文本时** Ctrl+C → Shell 模式发送 `\x03` / Agent 模式打断回合（原有行为不变）
6. Ctrl+V → 从剪贴板粘贴到终端（两种模式均可用）
7. Electron 打包版中上述行为一致

## 2. AI 大文件下载超时优化

### 2.1 问题

AI 代理通过 `run_command` 调用 wget/curl 下载大文件时，当前 60 秒执行超时过短导致失败。SFTP 传输的无进度超时 120 秒同样偏短。

### 2.2 方案

将两条链路的超时分别调整，同时保留空闲检测作为心跳机制。

### 2.3 PTY 命令执行链路（run_command）

**现状分析**：
- `SettingsService.DEFAULT_RUN_COMMAND_TIMEOUT_SECONDS = 60`
- `PtyCommandScheduler` 有三项超时：idle timeout（无输出超时）、max absolute timeout（绝对上限）、watch（中断后观察窗口）
- watchdog 每次收到 stdout/stderr 数据时重置计时器，本质就是心跳检测

**调整**：
- `DEFAULT_RUN_COMMAND_TIMEOUT_SECONDS`：60 → **1800**（30 分钟）
- `V1__init_schema.sql` 种子行同步更新
- `PtyCommandScheduler` 的 `DEFAULT_MAX_ABSOLUTE_MS` 当前已是 30 分钟（BUG-A 修复时调整），无需再改；只需确认 settings 层的 `run_command.timeout.seconds` 与之一致
- 空闲超时（idle timeout）保持 120 秒不变——远端长时间无任何输出即判定假死

**心跳检测**：当前 watchdog 机制已实现心跳语义——有数据流 = 心跳正常 = 重置计时器；无数据流超过 idle timeout = 判定中断 = 发送 Ctrl-C。无需新增心跳协议。

### 2.4 SFTP 传输链路

**调整**：
- `TransferProperties.progressTimeoutSeconds`：120 → **300**（5 分钟无进度即失败）
- SFTP 传输有持续字节流，5 分钟无进展基本确认连接已断

### 2.5 影响范围

- 后端：`SettingsService`（默认值）、`V1__init_schema.sql`（种子行）、`SshProperties`（exec 超时注释）、`TransferProperties`（progress 超时）
- 测试：更新相关超时断言
- 不涉及前端/契约变更

### 2.6 验证场景

1. AI 通过 `run_command` 执行 `wget` 下载 >100MB 文件 → 30 分钟内完成不被中断
2. 下载过程中有持续输出（wget 进度条）→ watchdog 不断重置 → 不触发空闲超时
3. 下载过程中远端 SSH 断开 → 空闲超时触发 → 命令被中断 → 模型收到超时反馈
4. SFTP 下载大文件 → 5 分钟无字节进展才判定失败
5. 短命令（ls、cat 小文件）不受影响，仍快速完成

## 3. Agent 上下文超限——摘要 + 分块组合方案

### 3.1 问题

AI 读取超大文本文件时出现上下文超限错误。现有保护机制（60 条窗口、头尾投影、淘汰、单次恢复）在单条 `read_file` 返回 500 行大文件内容时仍可能耗尽 token 预算。

### 3.2 方案

对 `read_file` 工具做两阶段改造：先摘要给模型全貌，模型再按需分块深入读取。

### 3.3 分块读取（read_file 增加行范围参数）

- `read_file` 工具签名增加 `start_line` 和 `end_line` 可选参数
- 不传范围时行为不变（读前 N 行，受 `read_file.max_lines` 限制）
- 传范围时只返回指定行区间内容，并在结果头部标注 `[行 X-Y / 总 Z 行]`
- 模型可像 `sed -n 'X,Yp'` 一样精确读取感兴趣的区域

### 3.4 服务端摘要（大文件自动摘要）

当 `read_file` 无范围读取且达到行数上限时，在截断提示之外附加结构摘要：
- 文件总行数（通过 `wc -l` 获取，额外一次轻量 exec）
- 前 20 行（文件头部，通常含结构/格式信息）
- 末尾 10 行（文件尾部，通常含汇总/结束标记）
- 中间段提示："中间 N 行未返回，请用 read_file(path, start_line, end_line) 按需读取"

### 3.5 系统提示增强

在 `AgentSystemPrompt` 的工具纪律中补充：
- 大文件（>100 行）先用 `wc -l` 查行数了解规模
- 用 `read_file` 的行范围参数分段读取感兴趣的区域
- 不要一次读取整个日志文件
- 优先用 `grep -n` 定位关键行号后再精确读取

### 3.6 影响范围

- 后端：`AgentTools.java`（read_file 签名 + 摘要逻辑）、`AgentSystemPrompt.java`（提示词）
- 测试：`AgentToolsTest` 补充范围读取和摘要用例
- 不涉及前端/契约变更（工具参数变化对前端透明）

### 3.7 验证场景

1. `read_file("/var/log/large.log")` 达到 500 行上限 → 返回头部 20 行 + 尾部 10 行 + 总行数 + 截断提示
2. `read_file("/var/log/large.log", start_line=100, end_line=200)` → 只返回第 100-200 行 + 总行数标注
3. 模型先 `wc -l` 查行数 → 再分块读取关键区域 → 不再触发上下文超限
4. 小文件（<500 行）行为不变，不附加摘要开销
5. 现有上下文恢复机制（单次恢复、历史减半）仍正常工作

## 4. 版本分支管理

### 4.1 方案

在当前 `main` 上打 `v0.1.0` tag 标记已发布版本，然后三仓各自创建 `feature/v0.2.0-improvements` 分支用于新功能开发。

### 4.2 分支创建流程

```powershell
# 1. 主控仓库打 tag + 创建 feature 分支
git tag -a v0.1.0 -m "release: v0.1.0 desktop client"
git checkout -b feature/v0.2.0-improvements

# 2. frontend 子仓库
cd frontend
git tag -a v0.1.0 -m "release: v0.1.0"
git checkout -b feature/v0.2.0-improvements
cd ..

# 3. backend 子仓库
cd backend
git tag -a v0.1.0 -m "release: v0.1.0"
git checkout -b feature/v0.2.0-improvements
cd ..
```

### 4.3 远端同步

```powershell
# 推送 tag 和分支到远端
git push origin v0.1.0
git push origin feature/v0.2.0-improvements

# 子仓库同理
cd frontend && git push origin v0.1.0 && git push origin feature/v0.2.0-improvements && cd ..
cd backend  && git push origin v0.1.0 && git push origin feature/v0.2.0-improvements && cd ..
```

### 4.4 合并策略

开发完成后按现有子仓库闭环流程：
1. frontend/backend 的 feature 分支先合入各自 main，推送
2. 主控 feature 分支更新子仓库指针到这些最终提交
3. 主控 feature 分支合入主控 main，推送

### 4.5 保护规则

- `v0.1.0` tag 是不可变标记，指向发布时的确切提交
- `main` 分支在 feature 开发期间保持干净，只接受 ff 合并
- feature 分支命名遵循 `feature/v0.2.0-improvements` 格式

## 5. 实施顺序

建议按以下顺序实施（依赖关系从简到繁）：

1. **版本分支管理**（最先）：打 tag、建分支，后续所有改动在 feature 分支上进行
2. **终端文本复制粘贴**（独立、最小改动）：前端 addon + 配置
3. **AI 大文件下载超时优化**（独立、配置调整）：后端超时参数 + 种子行
4. **Agent 上下文超限**（最复杂）：工具签名 + 摘要逻辑 + 提示词
